# ChurchTools Integration for Homematic IP
## Core idea
### CRON-based Heating

This service acts as a connector between the [ChurchTools Calendars](https://heidelsheim.church.tools/?q=churchcal#CalView/) and the Homematic IP Access Point in the community hall. In ChurchTools, events can be created that include room bookings. When a room is booked (especially in winter or on cold days), the heating units in that room should warm it to a predefined temperature.  
To achieve this, the system analyzes the current room temperature, the desired target temperature, and the room’s specific heating rate.

At every scheduled interval (as defined by the cron expression), the service evaluates all upcoming events with room bookings. For each event, it calculates the heating rate. If the time required to heat the room is less than the time remaining until the event starts, heating for that room is triggered.

### Monitoring

In addition to the cron job, the service maintains a WebSocket connection to the Homematic IP server. This WebSocket stream provides live updates about device states—such as set temperatures, current temperatures, humidity, and more. Each relevant update is written as a datapoint into [InfluxDB](https://influx.smarthome.cg-heidelsheim.de/).

Historical data is visualized in a [Grafana Dashboard](https://grafana.smarthome.cg-heidelsheim.de/d/DZJ-FUKnz/heizungsgruppen?orgId=3), including both sensor readings (e.g., temperatures) and logs generated by the script. These logs are also accessible via the [Grafana Log Dashboard](https://grafana.smarthome.cg-heidelsheim.de/d/A-73UbcVk/logging?orgId=3&refresh=5s), providing full insight into system behavior and automated actions.

## Detailed Functionality
### Cron Job
#### Midnight Reset
When the cron job runs at midnight, the system performs a temperature reset. For every room that was **manually changed** and not changed back, the temperature is restored to its base value (typically 16 °C).

To determine whether a room was changed manually, the system checks for an active **room lock**. If a lock exists, it means the temperature was changed automatically for an event—not manually. In this case, the room is **flagged**, so the reset can be re-attempted during the next cron run.

If a room *is not* locked, its default temperature is loaded and applied in Homematic.

The midnight reset process is executed up to **three times per iteration**. This is necessary because connection details (e.g., server URL) may change; if they do, the configuration is refreshed and the reset is retried.  

This retry mechanism is **not** related to locked rooms.  
If all three attempts fail, an error is reported to Uptime Kuma.

#### Resolve Locks
For each room, the lock state is checked. A lock indicates that the preheating cycle for that room has already been executed and that an event is currently taking place there.
The lock prevents further automatic changes from being applied.

```json
{
    "groupId": "Godi-Saal",
    "expiring": "<DATE>",
    "eventName": "Bandprobe"
}
```

For every active lock, its expiration time is evaluated. If the current date exceeds the expiration date, the lock is removed.
After removal, the room temperature is reset to **IDLE** (default 16 °C).

#### Fetch Events
For the configured calendars (referenced by ID in the `.env` file), events are loaded from the ChurchTools API.

#### Event Handling
On startup, only active or future events are processed. Past events may still appear in the API response but are ignored. Events without room bookings are also skipped.

For each current or upcoming event with valid room bookings (`status_id = 2`), the heating requirements for each room are calculated independently.

If a room is locked, it is excluded from further processing.

To determine the heating requirement for a room, the system compares the current temperature with the desired target temperature.
Each room has a **spinup time** (including a buffer timer), representing how long it takes for the radiators to warm up and the first temperature changes to become noticeable (depending on room size).
Additionally, a **minutesPerDegree** value is used to estimate how long the room takes to heat per degree, based on historical data.

The calculation is:
```js
requiredTime = spinUpTime + buffer + (degreeDifference * minutesPerDegree)
```

If `requiredTime` (in minutes) exceeds the time remaining until the event begins, heating for that room is triggered — but **only if no manual override is active**.
The system respects manual changes and will not overwrite them; automatic heating is simply delayed to the next cycle.

When heating successfully starts, a lock is created for that room.

### WebSocket Events
Each WebSocket message is filtered, and only three message types are currently processed.

#### Handle Group Message
A group message indicates that a heating group (room) has changed.
Non-heating groups are ignored.

For heating groups, the previous state is loaded and compared with the new state.
If there is a difference, the updated values are written to InfluxDB, and the new state is persisted on disk.

#### Handle Device Message
A device message indicates that a device with built-in sensors has reported a change.
Devices that are not heating thermostats are discarded.

For valid heating thermostats, the previous state is loaded.
Each channel (usually just one) is compared with the new state.
On any change, the updated data is written to InfluxDB, and the new state is persisted.

#### Handle Home Message
A home message provides updates about general home data, such as weather.
The previous location/home state is loaded and compared with the new values.
If differences are found, updated data is sent to InfluxDB, and the new state is persisted on disk.

# FAQ
## Room heating did not start
- Was there an actual booking of the room? 
- Is the room booking status accepted `status_id = 2`
- Is the room common, or is there a room that doesn't exist in Homematic?
